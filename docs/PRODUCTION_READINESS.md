## 2. Закрытые production-риски

- **Секретный код больше не утекает** через публичную ленту и `/api/requests/{id}`. Он доступен только автору заявки, назначенному волонтёру и координатору (`DataMaskingService`).
- **Точные координаты** скрыты из публичной ленты; расстояние считается на сервере.
- **Принятие заявки атомарно**: `UPDATE ... WHERE status='open'`; два волонтёра не могут взять одну заявку.
- **Завершение заявки атомарно**: повторное/параллельное завершение не начисляет карму дважды; блокировка после 5 неверных кодов тоже атомарна.
- **Отмена и переназначение** разрешены только для `open`/`in_progress`; завершённые заявки не переписываются.
- **SOS не режется по IP**: лимит привязан к авторизованному аккаунту и имеет запас для повторных нажатий.
- **SOS сохраняется до внешней отправки**: сбой адаптера не оставляет «фантомный» вызов без записи.
- **Честный статус 112**: API возвращает `dispatch_mode: "simulated"` и `emercom_notified: false`, пока не подключён реальный шлюз. UI больше не утверждает, что 112 оповещён.
- **Right to be forgotten** очищает не только адрес/код, но и заголовки, описания, отзывы, чат, медицинские заметки, контакты и данные допуска волонтёра.
- **Пароли и токены**: logout отзывает все stateless-токены через `token_version`; сброс пароля использует одноразовый атомарный claim.
- **Идентификация волонтёров**: эмуляторы МСИ/ЕСИА в production возвращают `PROVIDER_NOT_CONFIGURED`, пока не включён реальный провайдер; повторная проверка сбрасывает `is_verified`.
- **Публичная проверка бейджа** теперь загружает модели и проверяет отзыв волонтёра, а не только HMAC.
- **QR ведёт на человекочитаемую страницу** `/verify/{token}`, а не на JSON API.
- **Rate limiter** использует `flock` для атомарного read-modify-write.
- **Healthcheck** проверяет БД, crypto, auth и запись в `database`, `storage/logs`, `storage/cache`, `storage/metrics`; при проблеме возвращает 503.
- **Watchdog** запускается фоновым процессом в production-контейнере, а не только при открытии админки.
- **Демо-оповещение** о «лже-сантехниках» больше не создаётся в production (`SEED_DEMO=false`).
- **Автовход подопечного** в production по умолчанию выключен (`ELDERLY_AUTO_LOGIN=false`), а неявный demo-вход и `X-Demo-User` запрещены (`ALLOW_DEMO_AUTH=false`).
- **Документация** синхронизирована: убраны несуществующий `/family`, PostgreSQL и multi-stage claims, удалена сирена из UI/кода/документации.

## 3. Обязательный чек-лист перед публичным запуском

1. Скопировать `.env.prod.example` → `.env.prod`, заменить **все** секреты.
2. `APP_SECRET` — не короче 32 символов; `APP_ENCRYPTION_KEY` — строго `base64:` 32 байта, 64 hex или 32 raw-символа, иначе production вернёт 503.
3. Задать `APP_URL=https://<домен>` — от него строятся QR-ссылки.
4. Оставить `ELDERLY_AUTO_LOGIN=false` и `ALLOW_DEMO_AUTH=false` для многопользовательского режима.
5. Оставить `IDENTITY_PROVIDER_LIVE=false`, пока не подключён реальный шлюз МСИ/ЕСИА.
6. Подключить реальный адаптер МЧС/112 или явно принять, что `dispatch_mode=simulated`.
7. Проверить `docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build`.
8. Убедиться, что `/api/health` возвращает 200 и все `checks.*` в норме.
9. Проверить вход администратора, создание заявки, принятие/завершение волонтёром и `/verify/{token}`.
10. Настроить внешний алерт на `app_sos_alerts{status="ACTIVE"} > 0` и `app_db_up == 0`.
11. Хранить `APP_ENCRYPTION_KEY` отдельно от дампов БД.

## 4. Осознанные ограничения

- **Реальный 112/МЧС не подключён.** Это эмулятор с тикетом и офлайн-очередью; для реального запуска нужен договор и шлюз.
- **Реальная МСИ/ЕСИА не подключена.** Эмуляторы отключены в production fail-closed.
- **Миграции выполняются при старте контейнера.** Для нескольких реплик нужен отдельный init-job/миграционный lock; текущая схема рассчитана на один app-контейнер.
- **MySQL 8** — единственная БД для dev, test и production. Прежний файловый режим удалён из кода, Docker-образов, тестов и документации.
- **Rate limiter и счётчики метрик** хранятся в файлах контейнера; при горизонтальном масштабировании нужен общий Redis/volume. Текущий compose рассчитан на один app-контейнер.
- **Громкие звуковые эффекты/сирена отсутствуют** по требованиям доступности; мониторинг SOS должен опираться на визуальный баннер и внешние алерты.
