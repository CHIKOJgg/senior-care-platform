# ADR-0002. Vanilla JS + CSS без фронтенд-фреймворка и сборки

- **Статус:** Принято
- **Дата:** 2026-11-08
- **Категория:** Фреймворк / frontend
- **Связанные ADR:** [ADR-0001](0001-php82-custom-mvc.md), [ADR-0014](0014-web-speech-and-audio-api.md)

## Контекст

Основная аудитория платформы — пожилые люди, в том числе с плохим зрением, тремором рук, слабым интернетом и старыми устройствами. Требования:

- **WCAG 2.1 AAA**: контраст, крупные тач-таргеты, видимый фокус, семантика, `aria-live`;
- режим «для старшего поколения» со сверхкрупным шрифтом и высоким контрастом;
- голосовой ввод и озвучивание (Web Speech API);
- работа без этапа сборки и без Node.js в production;
- минимальный риск, что фреймворк «сломает» доступность или увеличит бандл.

При этом интерфейс должен поддерживать три роли, аналитические панели, таблицы, модальные окна, поллинг SOS и работу с геолокацией.

## Решение

Фронтенд реализован на **ванильном JavaScript (ES6+)** и **CSS3 custom properties**, без React/Vue/Svelte, без npm, без bundler и без TypeScript:

```text
public/index.php           — серверный HTML-каркас, role-based секции
public/css/accessibility.css — дизайн-система, senior-mode, focus-visible
public/js/app.js           — SPA-логика, API-клиент, рендеринг, поллинг
public/js/speech.js        — Web Speech API (STT/TTS) + голосовые команды SOS
public/verify.php          — отдельная публичная страница проверки бейджа
```

Ключевые решения:

- **CSS-переменные** (`:root`) и класс `body.senior-mode`, который переключает палитру, размеры шрифта (22/32px) и высоту кнопок (60px).
- **Иконки — 100% inline SVG**, без эмодзи и растровых спрайтов (политика Zero-Emoji).
- **Рендеринг** — шаблонные строки и `innerHTML`/`textContent` в `app.js`; данные приходят из REST API.
- **Состояние** — модульные переменные (`currentRole`, `currentUser`), `localStorage` для долгого входа подопечного, `sessionStorage` для staff-сессии.
- **Доступность** — `aria-label`, `role`, `aria-live`, `:focus-visible`, крупные кнопки, текстовые дубли иконок.

## Обоснование

1. **Доступность важнее «модности».** Ванильный DOM предсказуем: разработчик точно знает, какие элементы и атрибуты попадут в разметку. Фреймворк может добавить лишние обёртки, скрыть фокус или усложнить аудит WCAG.
2. **Старые устройства и браузеры.** Нет полифилов, гидратации и большого JS-бандла; страница быстрее становится интерактивной на слабом телефоне.
3. **Нет сборочной цепочки.** Не нужны Node.js, npm, lock-файлы, CI-шаг сборки и контроль версий ассетов. Это согласуется с нулевыми зависимостями backend (ADR-0006).
4. **Простота отладки.** В браузере виден реальный DOM и реальный код, а не скомпилированный/минифицированный бандл с source maps.
5. **Соответствие CSP.** Хотя текущая CSP допускает `unsafe-inline`, отсутствие внешних скриптов упрощает ужесточение политики в будущем.
6. **Голосовые API — нативные.** Web Speech API и Web Audio API не требуют фреймворковых обёрток.

## Последствия

### Положительные

- Минимальный вес страницы и быстрый first paint на 3G.
- Полный контроль над семантикой и ARIA.
- Нет зависимости от жизненного цикла и breaking changes UI-фреймворка.
- Легко тестировать текстовые маркеры и наличие ARIA-атрибутов (см. `tests/test_frontend_wcag.php`).
- Один и тот же код работает в dev и prod без сборки.

### Отрицательные / риски

- **Ручное управление DOM.** Много императивного кода, риск рассинхронизации состояния и разметки; `app.js` разрастается.
- **Нет реактивности и компонентной модели.** Повторное использование UI-блоков ограничено функциями и шаблонными строками.
- **Нет типизации.** Ошибки в структурах API ловятся только тестами и в runtime.
- **Риск XSS при `innerHTML`.** Часть данных приходит с сервера; нужна дисциплина экранирования (на backend есть `htmlspecialchars`, на клиенте — `textContent` там, где возможно).
- **Сложнее масштабировать команду.** Новым разработчикам может не хватать привычных паттернов React/Vue.
- **Нет SSR-гидратации.** Первый рендер — серверный HTML, дальше данные догружаются поллингом.

### Нейтральные

- CSS-дизайн-система построена на переменных и утилитарных классах; это ближе к «design tokens», чем к CSS-in-JS.
- Поллинг вместо WebSocket: проще, но создаёт постоянный трафик.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **React** | Требует сборки, зависимостей и гидратации; риск ухудшить доступность и увеличить бандл. Избыточен для 3 ролей и десятка экранов. |
| **Vue** | Проще React, но всё равно Node.js, сборка, экосистема и обновления; не даёт решающего выигрыша. |
| **Svelte** | Отличный размер бандла, но добавляет компилятор и toolchain; проект сознательно избегает сборки. |
| **Alpine.js / HTMX** | Лёгкие, но всё же внешние зависимости и иной стиль мышления; текущий объём логики можно удержать на ванильном JS. |
| **jQuery** | Устаревший подход, лишний вес, не решает доступность. |
| **TypeScript** | Полезен, но требует сборки/транспиляции; при выбранном «no-build» подходе несовместим без компромиссов. |
