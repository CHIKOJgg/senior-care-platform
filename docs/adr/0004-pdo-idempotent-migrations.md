# ADR-0004. PDO и идемпотентные миграции на чистом PHP

- **Статус:** Принято
- **Дата:** 2026-11-08
- **Категория:** База данных
- **Связанные ADR:** [ADR-0003](0003-database-sqlite-mysql.md), [ADR-0006](0006-zero-composer-custom-libraries.md)

## Контекст

Схема развивалась итеративно: добавлялись поля геозоны (`completed_lat`, `completed_lon`, `distance_to_target`), watchdog (`is_overdue`, `assigned_at`, `failed_attempts`), верификация (`verification_status`, `badge_token`), согласия (`revoked_at`), сброс пароля (`password_resets`), SOS (`sos_alerts`).

Требования:

- не терять данные при обновлении;
- безопасно запускать миграции повторно (CI, рестарт контейнера, несколько деплоев);
- поддерживать и SQLite, и MySQL;
- не вводить миграционный фреймворк и Composer-зависимости;
- автоматически доводить старые данные до нового формата (например, шифровать legacy `mobility_notes`).

## Решение

Доступ к данным — **PDO + prepared statements**, без ORM. Миграции — **собственный идемпотентный скрипт** `database/migrate.php`.

### PDO

- Singleton `Database::getConnection()` с `PDO::ATTR_ERRMODE => ERRMODE_EXCEPTION` и `FETCH_ASSOC`.
- Все запросы с параметрами — `prepare()` + `execute()`.
- `Model::where()` валидирует имя колонки регуляркой `^[a-zA-Z0-9_]+$` и оператор по белому списку.
- `Model::create()`/`update()` фильтруют ключи по тому же шаблону.
- Транзакции используются в критичных операциях (обезличивание, сброс пароля).

### Миграции

`database/migrate.php`:

1. Определяет драйвер (`PDO::ATTR_DRIVER_NAME`) и выбирает `schema.sql` или `schema.mysql.sql`.
2. Проверяет существование таблиц через `sqlite_master` или `INFORMATION_SCHEMA`.
3. Получает колонки через `PRAGMA table_info()` или `INFORMATION_SCHEMA.COLUMNS`.
4. Добавляет отсутствующие колонки через `ALTER TABLE ... ADD COLUMN` (только если их нет).
5. Применяет базовую схему: `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`.
6. Для SQLite отдельно гарантирует 13 индексов.
7. Синхронизирует `verification_status` со старым `is_verified`.
8. Находит незашифрованные `mobility_notes` и шифрует их через `CryptoService` с префиксом `enc:v1:`.

Для MySQL SQL-файл выполняется по одному стейтменту (разбиение по `;`), для SQLite — целиком.

## Обоснование

1. **Идемпотентность.** Скрипт можно запускать при каждом старте контейнера (`docker/entrypoint.sh`, `Dockerfile`) — он не падает на существующих объектах и не дублирует колонки.
2. **Нет downtime-миграций «всё сразу».** Добавление nullable-колонок и `CREATE ... IF NOT EXISTS` безопасно для работающей системы.
3. **Данные не теряются.** Нет `DROP TABLE`/`TRUNCATE`; исторические записи сохраняются, а чувствительные поля шифруются на месте.
4. **Кросс-СУБД.** Ветвление по драйверу позволяет одному скрипту обслуживать SQLite и MySQL.
5. **Прозрачность.** Каждый шаг логируется (`[MIGRATE] Added column...`), что удобно в CI и при разборе инцидентов.
6. **Нет зависимости от Phinx/Doctrine.** Это согласуется с ADR-0006 и уменьшает поверхность атаки.

## Последствия

### Положительные

- Рестарт контейнера не требует ручных действий.
- CI и production используют один и тот же механизм.
- Легко добавить новую nullable-колонку: одна запись в массиве `$hrAdditions`/`$vpAdditions` + schema-файлы.
- Автоматическая криптомиграция legacy-данных.

### Отрицательные / риски

- **Нет down-миграций.** Откат изменений схемы не автоматизирован.
- **Нет таблицы версий.** Порядок и факт применения отслеживаются по фактическому наличию колонок, а не по `schema_migrations`.
- **Риск рассинхронизации.** `migrate.php` и оба schema-файла нужно обновлять согласованно.
- **Разбиение MySQL-файла по `;`** хрупко, если внутри появятся процедуры/триггеры с `;`.
- **Долгие блокировки.** `ALTER TABLE` на больших MySQL-таблицах может блокировать запись; для больших объёмов нужен online-DDL/окно обслуживания.
- **Нет checksum/контроля изменений.** Кто-то может вручную изменить схему, и это не будет замечено.

### Нейтральные

- Скрипт запускается и в entrypoint production, и в CI, и вручную.
- Шифрование legacy-заметок выполняется при каждом запуске, но только для незашифрованных строк.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **Phinx** | Composer-зависимость, отдельный CLI и конфиг; избыточен для 12 таблиц. |
| **Doctrine Migrations** | Тянет Doctrine DBAL/ORM, сложен и не нужен без ORM. |
| **Laravel migrations** | Требует Laravel/Composer; противоречит выбранному стеку. |
| **Ручные SQL-файлы** | Не идемпотентны, легко забыть применить, нет автоматизации в entrypoint. |
| **Полный пересоздание схемы** | Потеря данных и downtime; неприемлемо для production. |
