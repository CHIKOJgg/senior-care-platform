# ADR-0009. Адаптер МЧС 112 и офлайн-очередь SOS

- **Статус:** Принято
- **Дата:** 2026-11-08
- **Категория:** Интеграция
- **Связанные ADR:** [ADR-0006](0006-zero-composer-custom-libraries.md), [ADR-0010](0010-observability-stack.md)

## Контекст

Кнопка SOS — критическая функция: пожилой человек может нажать её при падении, боли или угрозе. Требования:

- сигнал должен создавать запись с **приоритетом 0** и мгновенно попадать координатору ТЦСОН;
- должна быть возможность передать вызов в **МЧС 112**;
- при недоступности внешнего шлюза вызов **не должен теряться**;
- интеграция должна быть заменяемой (реальный 112, другой шлюз, тестовый адаптер);
- координатор должен видеть квитанцию, статус и уметь разрешить инцидент.

Реальный API 112 в учебном/демо-проекте недоступен; нужна эмуляция с правдоподобными контрактами.

## Решение

### Интерфейс и адаптер

```text
app/Services/Emergency/
├── EmergencyAlertAdapterInterface.php
└── MchsEmergencyAdapter.php
```

`EmergencyAlertAdapterInterface` описывает:

- `getProviderName()`;
- `dispatchEmergency(array $incidentData)`;
- `checkIncidentStatus(string $ticketId)`;
- `cancelIncident(string $ticketId, string $reason)`.

`MchsEmergencyAdapter`:

- провайдер `EMERCOM_112_BY`;
- квитанция `EMERCOM-112-BY-YYYY-XXXX` (год + 4 hex);
- проверка формата квитанции регуляркой;
- назначенный расчёт `ПАСЧ-24 Советского РОЧС г. Минска (АЦ-5.0)`;
- ETA 5–7 минут;
- логирование факта отправки в `Logger::security`;
- **offline-очередь**: при `simulate_network_failure` инцидент кладётся в статический `$offlineQueue`, ответ содержит `queued_offline: true`.

### Поток SOS

1. `POST /api/sos` (см. `SosController`).
2. Координаты берутся из запроса, иначе из `elderly_profiles`.
3. Создаётся `sos_alerts` со статусом `ACTIVE`, `priority = 0`, адресом, причиной.
4. Вызывается `MchsEmergencyAdapter::dispatchEmergency()`.
5. `emercom_ticket_id` сохраняется в БД.
6. Координатор видит активные вызовы через `GET /api/sos/active` / `GET /api/coordinator/sos-alerts`.
7. Разрешение — `POST /api/sos/{id}/resolve`, статус `RESOLVED`, `resolved_at`.

### UI

- Кнопка SOS с `min-height: 60px`, `aria-label`, подтверждением и озвучиванием.
- Пульсирующий баннер `sos-pulse-banner`, `aria-live="assertive"`.
- Сирена на Web Audio API (см. ADR-0014).

## Обоснование

1. **Изоляция внешнего шлюза.** Контроллер и БД не знают, как именно отправляется вызов; замена провайдера — новый адаптер.
2. **Offline resilience.** Даже при сбое сети инцидент фиксируется локально и возвращает подтверждение, а не 500.
3. **Правдоподобный контракт.** Квитанция, расчёт и ETA создают реалистичный сценарий для демонстрации и тестов.
4. **Приоритет 0.** Явное поле `priority` и отдельная таблица `sos_alerts` позволяют строить очередь и алерты независимо от обычных заявок.
5. **Аудит.** `Logger::security` фиксирует факт отправки, координаты и ID.
6. **Нет Composer-зависимостей.** Достаточно `random_bytes` и `preg_match`.

## Последствия

### Положительные

- SOS-сценарий полностью работает без внешнего API.
- Легко подключить реальный шлюз (заменить адаптер/добавить HTTP-клиент).
- Координатор видит квитанцию и статус.
- Ошибка сети не приводит к потере инцидента в рамках процесса.

### Отрицательные / риски

- **Offline-очередь в памяти.** `static array` живёт только в рамках PHP-процесса; после рестарта или между воркерами очередь теряется. Для production нужна персистентная очередь (БД/Redis) и воркер.
- **Нет реальной отправки в 112.** Это эмулятор; юридически значимая передача требует сертифицированного шлюза и договора.
- **Нет идемпотентности.** Повторный вызов создаёт новый тикет; нужен idempotency key.
- **Нет retry/backoff.** Offline-запись не переотправляется автоматически.
- **Нет подтверждения от диспетчера.** Статус `DISPATCHED` — локальный, не подтверждение МЧС.
- **Ложные SOS.** Нет отмены/верификации; координатор должен уметь быстро снять ложный вызов.
- **Персональные данные в логах.** Адрес и координаты пишутся в security-лог; нужна политика хранения.

### Нейтральные

- `checkIncidentStatus()` возвращает фиксированный `DISPATCHED`; после интеграции должен читать реальный статус.
- ETA различается (7 минут при отправке, 5 при проверке) — это демонстрационная деталь.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **Прямой HTTP-вызов 112 из контроллера** | Нет публичного API, жёсткая связанность, невозможно тестировать. |
| **SMS-шлюз** | Платно, требует провайдера, не гарантирует доставку и не даёт квитанцию. |
| **Очередь Redis/RabbitMQ** | Дополнительная инфраструктура; для текущего масштаба избыточна, но нужна для production-resilience. |
| **Только запись в БД без адаптера** | Не даёт квитанции и интерфейса замены; сложнее подключить реальный шлюз. |
| **Внешний сервис-агрегатор** | Зависимость, стоимость, вопросы ПДн и юрисдикции. |
