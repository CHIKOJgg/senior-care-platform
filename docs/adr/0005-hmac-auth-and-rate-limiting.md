# ADR-0005. Stateless HMAC-токены, `token_version` и файловый rate limiter

- **Статус:** Принято
- **Дата:** 2026-11-08
- **Категория:** Безопасность
- **Связанные ADR:** [ADR-0006](0006-zero-composer-custom-libraries.md), [ADR-0011](0011-docker-caddy-nginx-phpfpm.md), [ADR-0013](0013-backups-secrets-healthchecks.md)

## Контекст

Нужна аутентификация для четырёх ролей и двух режимов:

- **Подопечный** открывает `/` без входа; родственник один раз входит с галочкой «Запомнить на этом телефоне» — устройство помнит вход до 365 дней.
- **Сотрудник** (координатор, волонтёр, администратор) входит через `/family`; сессия живёт только в текущей вкладке.
- Нужны смена пароля, «Выйти на всех устройствах» и отзыв всех ранее выданных токенов.
- Инфраструктура не должна требовать Redis/сессионного хранилища.
- Нужна защита от брутфорса логина и подбора кодов.

## Решение

### Токены

`app/Services/AuthService.php` создаёт **stateless HMAC-SHA256 токен**:

```text
token = base64(json(payload)) . "." . hex(hmac_sha256(base64(json(payload)), APP_SECRET))
```

Payload:

```json
{
  "user_id": 2,
  "role_id": 2,
  "role_code": "volunteer",
  "phone": "+375...",
  "name": "...",
  "tv": 1,
  "iat": 1730000000,
  "exp": 1730604800
}
```

- `TTL_SESSION = 7 дней`, `TTL_DEVICE = 365 дней`.
- Источники токена: `Authorization: Bearer`, `X-Auth-Token`, cookie `auth_token`.
- Подпись проверяется через `hash_equals()` (защита от timing-атак).
- `exp` проверяется на сервере.
- В production без `APP_SECRET` выбрасывается исключение; в local допускается dev-секрет.

### Отзыв токенов

В `users` есть `token_version` (по умолчанию 1). При смене пароля, сбросе или «Выйти на всех устройствах» значение увеличивается; токены со старым `tv` отклоняются. Это даёт мгновенный отзыв без хранения blacklist.

### RBAC

`AuthService::requireAuth(array $allowedRoles)`:

- 401, если пользователь не аутентифицирован;
- 403, если роли нет в списке;
- `admin` неявно получает доступ туда, где разрешён `coordinator`.

### Пароли

`password_hash()` / `password_verify()` с `PASSWORD_DEFAULT` (bcrypt). Пароли не хранятся в открытом виде и не логируются.

### Rate limiting

`app/Core/RateLimiter.php` — файловый счётчик в `storage/cache/rate_limits/*.json`:

- `check($key, $maxAttempts, $decaySeconds)` с `LOCK_EX`;
- логин: 10 попыток / 300 секунд на IP;
- смена пароля: 5 попыток / 300 секунд на пользователя;
- успешный логин очищает счётчик.

### Особый local-режим

В `APP_ENV=local` без токена `getCurrentUser()` возвращает администратора (демо-режим), а `X-Demo-User` позволяет выбрать пользователя. В production эта ветка недоступна.

## Обоснование

1. **Нет серверного session store.** Токен самодостаточен; PHP-FPM может работать в нескольких контейнерах без sticky sessions и Redis.
2. **Долгий вход для подопечного.** TTL 365 дней и cookie с `HttpOnly`, `SameSite=Lax`, `Secure` (при HTTPS) решают проблему «бабушка не может вводить пароль каждый раз».
3. **Мгновенный отзыв.** `token_version` в БД — простое и надёжное решение без blacklist и TTL-кэша.
4. **Stateless + БД-проверка.** Подпись проверяется криптографически, а актуальность пользователя и `tv` — по БД; это сочетает скорость и возможность отзыва.
5. **Минимум зависимостей.** Нет `firebase/php-jwt`, `lcobucci/jwt` и т.п. (см. ADR-0006).
6. **Простой rate limiter.** Для одного узла и низкого трафика файловых блокировок достаточно; не нужен Redis.

## Последствия

### Положительные

- Горизонтальное масштабирование без общего session store.
- Отзыв всех сессий одной операцией `token_version++`.
- Нет утечки паролей и токенов в логи.
- Простая реализация, которую можно построчно проверить.
- Работает с cookie и с API-клиентами (Bearer).

### Отрицательные / риски

- **Это не стандартный JWT.** Нет заголовка, `alg`, `kid`, стандартных claim-имён; сторонние JWT-библиотеки и API-шлюзы не смогут проверить токен «из коробки». Комментарии в коде называют его JWT, но фактически это собственный формат.
- **Смена `APP_SECRET` инвалидирует все токены.** Это ожидаемо, но требует согласованного деплоя.
- **Нет refresh-токенов и ротации.** Долгоживущий токен (365 дней) при краже действует долго; отзыв возможен только через `token_version`.
- **Файловый rate limiter не распределённый.** На нескольких узлах лимиты не общие; файлы нужно чистить/ротировать.
- **Demo-автологин опасен при неверном `APP_ENV`.** Если production случайно запущен с `APP_ENV=local`, любой получит администратора. Защита — обязательный `APP_ENV=production` в prod-конфиге.
- **Cookie без `__Host-` префикса** и `Secure` только при HTTPS; за TLS отвечает Caddy.
- **Нет CSRF-токена** для cookie-аутентификации; частично компенсируется `SameSite=Lax`, но требует отдельного решения при усилении безопасности.

### Нейтральные

- Токен передаётся и в заголовке, и в cookie — это удобно для разных клиентов, но расширяет поверхность.
- В local-режиме роли переключаются без пароля, что ускоряет демонстрацию, но не должно попадать в prod.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **PHP-сессии** | Требуют общего хранилища при нескольких PHP-FPM, сложнее для API и мобильных клиентов. |
| **Стандартный JWT (firebase/php-jwt)** | Плюс зависимость и риск неправильной настройки `alg`; для внутренней системы достаточно HMAC-конверта. |
| **OAuth2 / OpenID Connect** | Избыточно: нет внешних клиентов и провайдера идентичности для входа сотрудников. |
| **Redis-сессии** | Дополнительный сервис и эксплуатация; не нужен при stateless-подходе. |
| **Только cookie-сессии** | Не покрывают API-клиентов и тесты; долгий вход подопечного всё равно требует отдельного механизма. |
| **Argon2id вместо bcrypt** | Возможен, но `PASSWORD_DEFAULT` уже даёт безопасный bcrypt и переносим без настройки. |
