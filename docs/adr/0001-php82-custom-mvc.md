# ADR-0001. PHP 8.2 и собственное MVC-ядро без фреймворка

- **Статус:** Принято
- **Дата:** 2026-11-08
- **Категория:** Фреймворк / backend
- **Связанные ADR:** [ADR-0002](0002-vanilla-js-frontend-wcag.md), [ADR-0004](0004-pdo-idempotent-migrations.md), [ADR-0006](0006-zero-composer-custom-libraries.md)

## Контекст

Платформа обслуживает четыре роли (подопечный, волонтёр, координатор ТЦСОН, администратор) и должна:

- работать на недорогом сервере и в Docker без тяжёлого runtime;
- быть полностью аудируемой: обработка ПДн, экстренные вызовы, криптография;
- разворачиваться одной командой (`php -S` или Docker) без сборки фронтенда;
- не зависеть от внешних пакетов и цепочки поставок;
- поддерживать строгую типизацию и предсказуемые ошибки.

Команда небольшая, а предметная область хорошо очерчена. Полноценный фреймворк с ORM, DI-контейнером, шаблонизатором и очередями дал бы больше возможностей, но и больше скрытой логики, зависимостей и требований к инфраструктуре.

## Решение

Используется **PHP 8.2+** с `declare(strict_types=1);` и **собственное лёгкое MVC-ядро**:

```text
public/index.php   — HTML-оболочка интерфейса
public/api.php     — front controller REST API + ручной автозагрузчик App\
public/verify.php   — публичная страница проверки QR-бейджа
app/Core/          — Router, Database, Model, Logger, RateLimiter, MetricsService
app/Controllers/   — Auth, HelpRequest, Coordinator, Volunteer, Sos, Privacy...
app/Models/        — User, HelpRequest, VolunteerProfile, SosAlert...
app/Services/      — Auth, Crypto, Privacy, GeoMatching, Badge, Watchdog...
database/          — schema.sql, schema.mysql.sql, migrate.php, seed.php
```

Ключевые элементы:

- **Router** (`app/Core/Router.php`) — regex-маршрутизация `GET/POST/PUT/DELETE`, параметры `{id}`, JSON-ответы, security-заголовки, запись метрик.
- **Model** (`app/Core/Model.php`) — тонкая обёртка над PDO: `all`, `find`, `where`, `create`, `update`, `delete`, `query`; имена колонок и операторы валидируются по белому списку.
- **Service layer** — бизнес-логика вынесена из контроллеров: криптография, маскирование, геоматчинг, бейджи, watchdog, согласия.
- **Front controllers** — `public/index.php` и `public/api.php` разделяют HTML-интерфейс и REST API.

## Обоснование

1. **Полный контроль над выполнением.** В системе есть чувствительные операции (расшифровка медицинских заметок, проверка секретного слова, отзыв токенов, обезличивание). Собственный код проще построчно проверить и объяснить регулятору/аудитору.
2. **Нулевые внешние зависимости.** Нет `composer.json`, `vendor/`, конфликтов версий и supply-chain-риска. Это осознанно связано с ADR-0006.
3. **Низкий порог эксплуатации.** Приложение запускается `php -S localhost:8000 router.php` или через PHP-FPM; не нужны Redis, брокеры, отдельный шаблонизатор или сборщик.
4. **Предсказуемая производительность.** Нет тяжёлого bootstrap фреймворка; на запрос выполняется только нужный код. Для социальной платформы района этого достаточно.
5. **Строгая типизация.** `strict_types=1` и типизированные сигнатуры уменьшают класс ошибок «строка вместо числа» в расчётах координат, TTL и лимитов.
6. **Соответствие требованиям ТЗ.** Документация проекта (`PROJECT.md`, `plan/01_SYSTEM_OVERVIEW.md`) прямо фиксирует «чистое PSR-4 модульное MVC-ядро на PHP 8.2 без внешних Composer-зависимостей».

## Последствия

### Положительные

- Кодовая база компактна и обозрима; нет «магии» фреймворка.
- Быстрый старт для нового разработчика: достаточно знать PHP и PDO.
- Легко контейнеризировать и запускать в CI.
- Нет затрат на обновление фреймворка и миграцию между мажорными версиями.
- Все security-решения (заголовки, CORS, JSON-ошибки) видны в одном месте.

### Отрицательные / риски

- **Собственный фреймворк нужно поддерживать.** Нет готовых middleware, валидации, DI, событий, очередей, локализации.
- **Частичное соответствие PSR-4.** Автозагрузчик написан вручную в `public/api.php`; сторонние инструменты (PHPStan, Psalm, IDE) не получат composer-автозагрузку без дополнительной настройки.
- **Слой View не выделен.** `views/` пуст; HTML живёт в `public/index.php`, логика — в `public/js/app.js`. Это снижает чистоту MVC и усложняет переиспользование шаблонов.
- **Нет встроенной защиты от типовых атак.** CSRF, массовое присвоение, IDOR и т.п. нужно закрывать вручную (часть уже закрыта RBAC и проверками владельца).
- **Риск «расползания» контроллеров.** Без архитектурных ограничений бизнес-логика может снова начать протекать в контроллеры.

### Нейтральные

- Маршруты описаны императивно в `public/api.php`, а не декларативно; это удобно для чтения, но не даёт автогенерации OpenAPI.
- Тестирование построено на собственном harness (ADR-0012), а не на PHPUnit.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **Laravel** | Требует Composer, Eloquent, Blade, очереди и много инфраструктуры; избыточен для 12 таблиц и 35+ эндпоинтов. Скрывает SQL и усложняет аудит. |
| **Symfony** | Модульный, но тяжёлый bootstrap и большое число компонентов; для небольшой команды выше стоимость сопровождения. |
| **Slim** | Ближе к минимализму, но всё равно требует Composer и отдельного выбора ORM, auth, шаблонов; в итоге получился бы «свой фреймворк» поверх Slim. |
| **Laminas / Mezzio** | Высокий порог входа и церемониальность; неоправданно для домена. |
| **Чистые PHP-скрипты без MVC** | Быстро на старте, но быстро приводит к дублированию, отсутствию RBAC-централизации и трудностям тестирования. |
| **PHP 8.3/8.4** | Новее, но 8.2 — широко доступная LTS-подобная версия с нужными возможностями (readonly, enums, first-class callable). Обновление возможно без изменения архитектуры. |
