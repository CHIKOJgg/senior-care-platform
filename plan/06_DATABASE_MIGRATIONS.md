# Реляционная схема базы данных, индексы и идемпотентные миграции
## Архитектура хранения данных платформы «ЗаботаРядом» (SQLite / PDO)

### 1. Архитектура хранилища и реляционная целостность
В качестве базы данных платформы используется встраиваемая реляционная СУБД SQLite 3 (`database/database.sqlite`), работающая через слой абстракции PHP Data Objects (PDO).

- Режим журнала транзакций: Write-Ahead Logging (WAL) для высокой параллельной производительности.
- Принудительное соблюдение ограничений внешних ключей:
  `$pdo->exec("PRAGMA foreign_keys = ON;");`
- Каскадные политики удаления:
  - `ON DELETE CASCADE` для связанных профилей пользователей (`elderly_profiles`, `volunteer_profiles`), журналов согласий (`user_consents`) и вызовов SOS.
  - `ON DELETE SET NULL` для поля `help_requests.volunteer_id`, гарантирующее сохранение заявки и её истории при блокировке или удалении учётной записи волонтёра.

---

### 2. Спецификация таблиц базы данных (12 сущностей)

1. **`roles`**: справочник ролей пользователей (`admin`, `coordinator`, `volunteer`, `elderly`).
2. **`users`**: базовые учётные записи (ID, уникальный телефон, хеш пароля, роль, статус активности, временные метки).
3. **`elderly_profiles`**: расширенные сведения о подопечном (домашний адрес, широта/долгота, год рождения, зашифрованные медицинские заметки `mobility_notes` [AES-256-GCM], контакты доверенных лиц).
4. **`volunteer_profiles`**: сведения о волонтёре (рейтинг, баллы кармы, статус модерации ТЦСОН `verification_status` [`PENDING`, `VERIFIED`, `REJECTED`], маскированные паспортные данные, статус проверки МВД, активный токен бейджа и срок действия).
5. **`categories`**: классификатор направлений помощи (продукты, лекарства, сопровождение, бытовые работы) с нормативными лимитами времени.
6. **`help_requests`**: заявки на оказание помощи. Включает координаты подопечного, секретное проверочное слово, статус (`open`, `in_progress`, `completed`, `cancelled`), координаты завершения волонтёра (`completed_lat`, `completed_lon`), расчётное расстояние (`distance_to_target`), счётчик ошибок кода (`failed_attempts`), флаг просрочки (`is_overdue`) и таймштамп взятия в работу (`assigned_at`).
7. **`chat_messages`**: защищённый внутриплатформенный чат между волонтёром, подопечным и координатором.
8. **`educational_materials`**: памятки и обучающие аудиоматериалы по цифровой грамотности и самопомощи.
9. **`fraud_alerts`**: оперативные оповещения ТЦСОН о выявленных схемах телефонных и финансовых мошенников.
10. **`volunteer_achievements`**: цифровые знаки отличия и награды за гражданскую активность.
11. **`user_consents`**: юридически значимый реестр согласий на обработку ПД по Закону РБ № 99-З с фиксацией IP, типа согласия и даты отзыва.
12. **`sos_alerts`**: журнал экстренных сигналов бедствия (Приоритет 0) с номерами квитанций МЧС 112 и геопривязкой.

### 3. Спецификация 11 производительных и уникальных индексов
Для обеспечения быстродействия поисковых запросов и предотвращения сканирования таблиц (Table Scan) в БД созданы 11 специализированных B-Tree индексов:

1. `idx_user_consents_user_id` ON `user_consents(user_id)` — быстрый поиск истории согласий субъекта ПД.
2. `idx_user_consents_type` ON `user_consents(consent_type)` — фильтрация по категориям юридических согласий.
3. `idx_sos_alerts_elderly_id` ON `sos_alerts(elderly_id)` — мгновенная выборка экстренных инцидентов гражданина.
4. `idx_sos_alerts_status` ON `sos_alerts(status)` — фильтрация активных инцидентов (`ACTIVE`) для диспетчера.
5. `idx_sos_alerts_priority` ON `sos_alerts(priority)` — сортировка очереди тревог по уровню срочности (Приоритет 0).
6. `idx_sos_alerts_created_at` ON `sos_alerts(created_at)` — хронологическая лента оперативного журнала.
7. `idx_help_requests_status` ON `help_requests(status)` — выборка открытых и выполняемых заявок в районе.
8. `idx_help_requests_is_overdue` ON `help_requests(is_overdue)` — моментальная выборка просроченных задач сторожевым таймером (Watchdog).
9. `idx_help_requests_assigned_at` ON `help_requests(assigned_at)` — эффективный расчёт времени нахождения задачи в работе.
10. `idx_volunteer_profiles_status` ON `volunteer_profiles(verification_status)` — формирование очереди модерации кандидатов.
11. `idx_volunteer_profiles_badge_token` UNIQUE ON `volunteer_profiles(badge_token)` — поиск и валидация динамического QR-бейджа за время $O(1)$.

### 4. Алгоритм неразрушающих идемпотентных миграций (`database/migrate.php`)
Скрипт миграций разработан с расчётом на непрерывное развёртывание без остановки обслуживания и без потери накопленных данных:
1. **Интроспекция схемы**: скрипт опрашивает существующие таблицы через системную команду `PRAGMA table_info(table_name)`.
2. **Инкрементальное расширение**: новые поля (`completed_lat`, `distance_to_target`, `is_overdue`, `assigned_at`, `failed_attempts` и др.) добавляются через безопасную команду `ALTER TABLE ... ADD COLUMN ...` только в том случае, если поле отсутствует.
3. **Безусловная безопасность**: создание новых таблиц выполняется строго с модификатором `CREATE TABLE IF NOT EXISTS`, а индексов — `CREATE INDEX IF NOT EXISTS`.
4. **Фоновая миграция криптографии**: скрипт выявляет исторические незашифрованные записи `mobility_notes` и прозрачно шифрует их мастер-ключом AES-256-GCM с простановкой префикса `enc:v1:`.
5. **Синхронизация статусов**: автоматическое приведение статусов верификации волонтёров к нормативному формату (`VERIFIED` / `PENDING`).
